# Задача: аудит и реализация «Отношений с жителями»

Работай по плану ниже. Не ограничивайся изменением файлов: сначала проведи аудит существующей реализации и исходных данных, затем внеси изменения.

Главный принцип: **не считать приведённые ниже факты подтверждёнными, пока они не проверены по исходным файлам, коду, конфигурациям, SNBT, loot tables и другим доступным источникам.**

## Контекст

Целевой предмет:

`society:face_note`

Название:

`Отношения с жителями`

Предмет показывает отношение всех жителей к игроку.

Нужно добавить раскрывающую информацию через `[Shift]`, которая сообщает игроку о практической ценности прокачки отношений, но при этом не дублирует уже существующую информацию без необходимости.

---

# Этап 1. Инвентаризация проекта

Перед изменениями определить:

где находится исходный проект;

где находятся KubeJS-скрипты;

где находится локализация;

где находятся данные Society;

где находятся данные о жителях и подарках;

где находятся FTB Quests;

где находится `villagers.snbt`;

где находится `ftbquestlocalizer`;

какие существующие скрипты используются для синхронизации файлов с игрой.

Не создавать новые файлы и не изменять существующие до завершения инвентаризации.

---

# Этап 2. Аудит механики дружбы

Проверить фактическую механику отношений.

Предварительно предполагается:

`0–500` очков;

`100` очков = `1 ♥`;

разговор даёт `+5`;

подарки дают значения порядка `+40 / +25 / +10 / -15 / -30`;

между подарками существует кулдаун `4 дня`.

Это **гипотезы для проверки**, а не исходные требования.

Нужно установить по исходному коду/данным:

какая фактическая шкала;

сколько очков соответствует одному сердцу;

как начисляются очки за разговор;

как начисляются очки за разные категории подарков;

есть ли дополнительные модификаторы;

как работают отрицательные подарки;

как работает ограничение на подарки;

какова фактическая длительность кулдауна;

что происходит при достижении каждого уровня отношений.

Отдельно определить, действительно ли награды появляются только на ♥5 или существуют значимые награды/эффекты на ♥1–♥4.

Не путать изменение диалогов с механической наградой.

Результат этого этапа записать в `audit_results.md`.

---

# Этап 3. Аудит наград

Провести полный аудит наград всех жителей.

Предварительно предполагается, что за ♥5 жители могут выдавать уникальные предметы, включая Книги навыков.

Проверить:

какие жители имеют награду за ♥5;

какой предмет выдаётся;

при каком точном условии;

есть ли альтернативная награда;

что происходит, если книга уже прочитана;

существуют ли жители без уникальной награды;

есть ли другие полезные награды, которые следует учитывать.

Сформировать таблицу:

| Житель | Роль | Награда ♥5 | Альтернативная награда | Условие | Источник |
| ------ | ---- | ---------- | ---------------------- | ------- | -------- |

Особое внимание уделить трём предварительно найденным жителям:

Кэролайн → «Искусство экономить»

Леон → «Круглый год фермерства»

Вероника → «Долговая яма»

Проверить не только имена, но и соответствие книг реальной механике.

Если хотя бы один из этих фактов неверен — исправить его в итоговом отчёте и не переносить ошибку в тултип.

---

# Этап 4. Аудит предпочтений

Исходный файл:

`tasks/Отношения_с_жителями/Список_Предпочтений.md`

Сначала прочитать существующий файл и сохранить всю полезную информацию.

Затем привести его к структуре, удобной для дальнейшего анализа человеком и агентом.

Для каждого жителя желательно иметь:

имя;

роль;

уникальные особенности;

награду за ♥5;

альтернативную награду;

Любимые подарки;

Нравящиеся подарки;

Нейтральные;

Не нравящиеся;

Ненавистные.

Отдельно вынести универсальные категории:

Universal Loved;

Universal Liked;

Universal Disliked;

Universal Hated.

Не удалять данные только ради более красивого формата.

Если данные из старого файла расходятся с исходной механикой, сохранить информацию о расхождении и указать подтверждённую версию.

---

# Этап 5. Определить практическую ценность подарков

Нужно установить, какую информацию реально полезно дать игроку.

Ответить на вопрос:

«Почему игроку стоит прокачивать отношения с жителями?»

Особенно проверить идею:

> Подарки от жителей за ♥5 могут быть действительно крутыми.

Установить, насколько это утверждение справедливо.

Отдельно определить, можно ли рекомендовать конкретных трёх жителей:

Кэролайн;

Леона;

Веронику.

Если эти жители действительно дают наиболее интересные Книги навыков, подтвердить это фактами.

Не использовать формулировку «топ-3», если нет объективного основания считать их тремя лучшими.

---

# Этап 6. Аудит того, где игрок получает информацию

Исследовать существующие источники информации в сборке.

Проверить:

`Руководства > Жители > Карточки жителей на доске`;

FTB Quests;

`villagers.snbt`;

`ftbquestlocalizer`;

другие существующие страницы/руководства, если они обнаружатся при исследовании.

Для каждого источника определить:

какую информацию он предоставляет;

есть ли там предпочтения подарков;

есть ли универсальные подарки;

есть ли информация о наградах;

может ли игрок найти нужную информацию без внешней вики.

---

# Этап 7. Аудит FTB Quests

Найти страницы и квесты, связанные с жителями и отношениями.

Определить существующую структуру вкладки «Жители».

После этого оценить, где логичнее размещать:

информацию об универсальных подарках;

общую механику подарков;

персональные предпочтения;

информацию о наградах за ♥5.

Не менять FTB Quests автоматически.

Сначала дать рекомендацию, стоит ли туда добавлять информацию и почему.

---

# Этап 8. Проектирование [Shift]-подсказки

Только после завершения аудита определить содержимое тултипа.

Базовое состояние:

`[Удерживайте Shift для подробностей]`

При удержании Shift информация должна быть короткой и ориентированной на практическую пользу.

Предварительная идея:

сообщить, что высокая дружба может приносить ценные награды;

указать на ♥5;

при подтверждении механики назвать жителей, дающих Книги навыков.

Не перегружать `[Shift]` полной таблицей предпочтений.

Не дублировать информацию, которую игрок уже удобно получает в карточках жителей.
